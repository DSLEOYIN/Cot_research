# 广汽集团 AI 一体化平台 PRD

> 文档类型：产品需求文档（PRD）
> 文档状态：V1.0
> 更新时间：2026-06-21
> 适用范围：集团统一 AI 门户、能力中心、权限治理、Skill/MCP 技术编排

## 1. 产品定位

本产品不是单点 ChatBI，也不是多个 AI 小助手的集合，而是广汽集团统一的 AI 一体化平台。

平台目标是把集团内分散建设的问答助手、报表助手、制度助手、填单助手、流程助手等能力统一沉淀为：

- 统一对话入口
- 统一 Skill 编排体系
- 统一 MCP 原子能力底座
- 统一组织权限治理
- 统一发布、运营、监控与审计

在该平台中：

- `Skill` 是业务能力单元，例如销量分析、请假申请、车型资料检索、竞品分析。
- `MCP` 是原子工具能力，例如模型调用、知识检索、N2SQL、SQL 执行、表单提交、审批触发。
- `权限` 决定谁可以使用哪些 Skill、访问哪些数据域、触发哪些动作型能力。
- `统一 AI 门户` 承担集团员工的单一 AI 入口。

## 2. 项目背景

当前集团内多个项目采用“一个需求对应一个 AI 应用”的建设模式，典型问题包括：

- 每个项目单独建设对话 UI、会话管理、权限控制、日志监控，重复投入高。
- 同类能力无法复用，例如检索、模型调用、结构化数据查询、表单提交在多个系统中重复实现。
- 业务人员需要记住多个 AI 入口，使用体验割裂。
- 平台侧难以统一做权限、治理、灰度、监控、审计和成本控制。
- 新需求经常被当作新项目立项，导致交付周期长、维护成本高。

因此需要将集团 AI 建设从“多个助手项目”升级为“统一平台 + 可编排能力”的战略。

## 3. 产品目标

### 3.1 核心目标

1. 为集团员工提供统一 AI 门户，用自然语言完成查询、分析、检索和流程办理。
2. 将新增需求标准化为 Skill，将共用能力沉淀为 MCP，避免重复建设。
3. 通过组织、角色、数据域和动作权限控制，实现集团级统一治理。
4. 让开发、运维、业务管理员在同一平台完成能力设计、配置、测试、审核和发布。
5. 在一个产品内承载 ChatBI、知识助手、流程助手、填单助手等多类场景。

### 3.2 第一阶段目标

第一阶段聚焦“平台框架跑通”，覆盖：

- 统一 AI 门户原型
- 能力中心原型
- 组织与权限治理原型
- Skill/MCP 技术编排原型
- 基础运营监控原型

第一阶段不追求所有真实后端能力打通，但要求前端信息架构、数据模型和页面职责能直接承接后续真实开发。

### 3.3 非目标

第一阶段暂不包含：

- 完整生产级 IAM 改造
- 全集团统一审批流引擎替换
- 任意代码在线编辑执行
- 多模型智能调度优化
- 精细化成本结算与计费分摊

## 4. 用户角色

| 角色 | 主要诉求 | 典型页面 |
|---|---|---|
| 集团员工 | 通过统一 AI 门户完成问答、查询、资料检索、流程办理 | AI 助手、能力中心 |
| 部门管理员 | 管理本部门可用能力、开通策略、常见场景 | 能力中心、组织与权限 |
| 平台管理员 | 管理组织、角色、授权策略、灰度范围、审计规则 | 组织与权限、平台运营 |
| AI 开发者 | 配置 Skill、复用 MCP、联调工作流 | Skill 编排、MCP 治理 |
| 运维人员 | 检查底层能力状态、依赖阻塞、发布与回滚 | MCP 治理、平台运营 |

## 5. 核心设计原则

### 5.1 用户看场景，不看技术名词

普通员工不需要理解 Skill、MCP、Schema、工作流，只需要看到：

- 我能用什么能力
- 适合哪些业务问题
- 能输出什么结果
- 有没有权限用

### 5.2 管理层按治理对象设计，而不是按代码对象设计

管理台不仅管理 Skill/MCP，还必须管理：

- 组织
- 角色
- 数据域
- 授权策略
- 发布范围
- 审计与风险

### 5.3 技术资产下沉，业务资产上浮

Skill/MCP 是平台底层资产。前台与主管理台应以“业务能力”表达，对技术细节做分层披露。

### 5.4 一个入口，多类能力

平台不是只做 ChatBI，而是支持：

- 数据分析类
- 知识检索类
- 流程办理类
- 表单填写类
- 经营助手类
- 专业领域助手类

## 6. 产品结构

### 6.1 一级导航

建议一级导航调整为：

1. `AI 助手`
2. `能力中心`
3. `平台治理`

其中：

- `AI 助手`：统一对话入口，面向集团员工。
- `能力中心`：展示已开通能力、推荐能力、业务场景和能力详情。
- `平台治理`：承载组织权限、运营监控、Skill 编排、MCP 治理等管理能力。

### 6.2 平台治理二级导航

平台治理下建议至少拆分为五类工作区：

1. `平台总览`
2. `组织与权限`
3. `平台运营`
4. `Skill 编排`
5. `MCP 治理`

## 7. 关键产品对象

### 7.1 Skill

Skill 是业务能力单元，必须具备以下信息：

- 唯一标识
- 业务名称
- 场景描述
- 所属能力域
- 输入方式
- 输出类型
- 依赖 MCP
- 适用组织
- 所需数据权限
- 是否包含执行动作
- 风险等级
- 负责人
- 版本状态

### 7.2 MCP

MCP 是原子工具能力，必须具备以下信息：

- 唯一标识
- 分类
- 读写属性
- 所属系统
- 连接配置
- 输入输出契约
- 安全策略
- 健康状态
- 被引用范围
- 发布状态

### 7.3 组织与权限

权限治理必须支持四个维度：

- 组织维度：集团 / 子公司 / 部门
- 身份维度：员工 / 主管 / 管理员 / 开发者 / 运维
- 数据维度：销售 / 订单 / 库存 / 人力 / OA / 知识库
- 动作维度：查询 / 下载 / 提交 / 审批 / 写入 / 外呼

## 8. 页面设计

### 8.1 AI 助手

定位：集团员工统一 AI 工作入口。

核心能力：

- 自然语言提问
- 展示 Skill 执行链路
- 展示数据表、图表、文本结论
- 展示动作型任务状态，例如请假申请已提交
- 从回答结果继续追问

页面强调“场景与结果”，弱化底层技术术语。

### 8.2 能力中心

定位：员工和部门管理员查看“可用能力”的入口。

核心模块：

- 已开通能力
- 推荐能力
- 热门业务场景
- 能力详情
- 开通说明 / 适用组织 / 申请条件

能力中心不应该是“应用商店”心智，而是“集团 AI 能力目录”。

### 8.3 平台总览

定位：平台管理员总看板。

核心模块：

- 今日活跃用户
- 近 30 天调用量
- 活跃能力排行
- 子公司开通覆盖
- 异常能力告警
- 待处理编排 / 审核 / 发布事项

### 8.4 组织与权限

定位：集团级治理核心页面。

核心模块：

- 组织树
- 角色模板
- 可用能力矩阵
- 数据域授权策略
- 动作权限策略
- 灰度与试点范围
- 审批与审计记录

### 8.5 平台运营

定位：看平台运行效果，不看底层代码。

核心模块：

- 调用量趋势
- 成功率
- 平均耗时
- 热门能力
- 高失败能力
- 组织覆盖率
- 重点问题看板

### 8.6 Skill 编排

定位：业务能力技术编排工作区。

核心模块：

- Skill 列表
- Skill 详情
- 工作流步骤
- 测试控制台
- 依赖 MCP
- 适用组织
- 风险等级
- 审核与发布流转

### 8.7 MCP 治理

定位：技术底座工具治理工作区。

核心模块：

- MCP 列表
- 连接配置
- Schema
- 安全策略
- 健康检查
- 被引用影响面
- 环境与发布状态

## 9. 关键业务场景

### 9.1 数据分析场景

员工输入“本月中东公司销量多少”，平台自动选择数据分析 Skill，调用知识检索、N2SQL、SQL 执行、分析生成等 MCP，输出表格、图表和结论。

### 9.2 资料检索场景

员工输入“某车型参数和竞品差异”，平台选择车型知识检索 Skill，输出结构化资料与来源。

### 9.3 流程办理场景

员工输入“帮我请明天下午半天假”，平台识别为请假办理 Skill，调用人员信息、假勤规则和表单提交 MCP，生成并提交申请。

### 9.4 权限控制场景

销售子公司员工只能使用销售分析类 Skill，无法访问人力或财务数据域；HR 管理员可访问请假与审批 Skill；动作型 Skill 需要额外授权。

## 10. 数据与治理要求

### 10.1 权限要求

- Skill 授权必须支持按组织开通
- 数据域授权必须与 Skill 开通解耦
- 动作型 MCP 必须单独受控
- 高风险操作必须保留审计日志

### 10.2 发布要求

- Skill 与 MCP 支持独立版本管理
- 支持灰度到子公司或部门
- 支持快速回滚
- 发布前必须展示影响面

### 10.3 监控要求

- 记录能力级调用量
- 记录组织级使用分布
- 记录失败率和主要错误原因
- 记录高成本能力调用

## 11. 第一阶段交付范围

### 11.1 文档交付

- 集团 AI 一体化平台 PRD
- 详细开发文档
- 页面信息架构说明

### 11.2 前端交付

- 调整现有统一工作台信息架构
- 将用户侧从“Skill 商店”升级为“能力中心”
- 将管理侧升级为“平台治理”
- 补充组织与权限、平台运营页面原型
- 保留 Skill/MCP 技术编排页面

### 11.3 后续真实化方向

- 接入真实权限 API
- 接入真实 Skill/MCP 注册数据
- 接入组织与角色数据
- 接入调用监控与审计日志

## 12. 成功标准

第一阶段成功的判断标准不是“多了几个页面”，而是：

- 团队能用统一术语讨论集团 AI 平台，而不是讨论零散小助手
- 前端结构能清楚表达“用户层、治理层、技术层”
- 新需求可以被自然归类为新增 Skill、复用 MCP、配置权限的流程
- 现有原型可直接承接后续真实平台化开发
